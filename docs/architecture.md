# 구성안과 데이터 계약 초안

이 문서는 WorkBoard의 구현 경계와 첫 데이터 계약이다. 저장 방식만 IntraFlow를 참고한다. WorkBoard의 공통 업무 모델과 화면은 별도로 설계한다.

## 책임 경계

화면 → Service → Repository → PC별 SQLite

Service가 같은 로컬 트랜잭션에 업무 변경과 전송 대기 기록을 남긴다. 별도 Sync 작업자가 전송 대기 항목을 읽어 NAS JSON을 게시하고, 다른 PC의 스냅샷을 검증해 Repository를 통해 적용한다. 화면과 업무 Service는 NAS 파일을 직접 다루지 않는다.

| 영역 | 책임 | 금지 사항 |
| --- | --- | --- |
| domain | 업무 식별, 상태 전이, 권한과 값 규칙 | UI·파일 경로·SQL 의존 |
| services | 사용 사례, 권한 검사, 원자적 변경, 조회용 집계 | NAS 직접 기록 |
| storage | SQLite 모델, Repository, 마이그레이션, 로컬 트랜잭션 | NAS에 DB 파일 배치 |
| sync | JSON 직렬화·검증·게시·수신, 재시도와 충돌 상태 | 화면 우회 수정, DB 파일 복사 |
| ui | 표, 상세 편집, 현황, 가져오기 미리보기 | SQLite 직접 쓰기 |
| import_export | 엑셀 매핑·검사·미리보기, CSV 생성 | 검증 없이 대량 적용 |

현재 패키지에 없는 services와 import_export 디렉터리는 해당 단계를 구현할 때 추가한다. 실행 진입점은 workboard 명령이다. 설정 예시는 config.example.toml에 두고 실제 경로·인증 정보는 로컬 설정으로만 관리한다.

## 개념 데이터 모델

| 엔터티 | 핵심 정보 | 작성 권한 |
| --- | --- | --- |
| Project | ID, 이름, 설명, 활성 여부 | 프로젝트 편집자 |
| Scope | ID, 프로젝트 ID, 이름, 종류, 상위 범위 ID | 프로젝트 편집자 |
| Category | ID, 프로젝트 ID, 이름, 순서 | 프로젝트 편집자 |
| WorkItem | ID, 프로젝트·범위·분류 ID, 제목, 외부 참조, 삭제 표시 | 프로젝트 편집자 |
| Assignment | ID, 업무 ID, 담당자 ID, 기한, 취소 여부 | 프로젝트 편집자 |
| AssignmentProgress | 배정 ID, 상태, 진행도, 결과, 보류 사유, 수정 시각 | 해당 담당자 |
| ProgressHistory | ID, 배정 ID, 이전·새 값, 작성자, 시각 | 진행 변경과 함께 자동 추가 |
| SyncOutbox | 대상 스냅샷, 변경된 엔터티, 재시도 상태 | 로컬 Service·Sync |
| SnapshotCursor | 마지막 적용 개정, 해시, 수신 시각 | Sync |

모든 공유 엔터티 ID는 UUIDv4 문자열을 사용하고, 시각은 UTC ISO-8601, 기한은 YYYY-MM-DD로 기록한다. 같은 제목이나 같은 외부 참조도 범위가 다르면 다른 WorkItem이다. 검증 템플릿의 프로젝트·코드 버전·분야·Codebeamer 항목 ID 조합은 가져오기 중복 후보를 찾는 기준이며 공통 업무의 전역 고유 제약은 아니다.

한 업무에 복수 담당자가 필요하면 Assignment를 여러 개 둔다. 진행 값은 담당자별 AssignmentProgress에 속한다. 프로젝트 현황의 건수와 평균 진행도는 원본 배정·진행 값에서 계산하며 별도 집계 원본으로 저장하지 않는다. 동일 계정 여러 PC의 동시 쓰기는 첫 버전 운영 정책 확정 전까지 지원 대상으로 표시하지 않는다.

## 진행 변경 계약

1. Service가 사용자, 배정, 변경 가능 항목과 상태 규칙을 검사한다.
2. Repository가 AssignmentProgress를 갱신하고 ProgressHistory를 추가한다.
3. 같은 SQLite 트랜잭션에 사용자 공개 스냅샷의 SyncOutbox 항목을 기록한다.
4. 트랜잭션을 커밋한 뒤 화면에 로컬 저장 성공과 공유 대기 상태를 반환한다.
5. Sync가 나중에 NAS 게시를 시도한다. 게시 실패는 이미 성공한 로컬 변경을 취소하지 않는다.

담당자는 자신의 진행 상태와 결과만 수정한다. 프로젝트 편집자는 업무 정의와 배정을 관리한다. 관리자 권한이 있더라도 타인의 진행 값을 대신 쓰는 권한과 자동으로 합치지 않는다.

## NAS 스냅샷 계약

- 프로젝트별 정의 스냅샷은 프로젝트 편집자가 게시한다.
- 사용자별 공개 진행 스냅샷은 해당 사용자만 게시한다. 다른 사용자의 파일은 앱에서 읽기 전용이다.
- 스냅샷에는 schema_version, project_id, author_id, revision, updated_at, payload, checksum을 둔다.
- 파일은 같은 파일 시스템의 임시 경로에 완전히 쓴 뒤 원자적으로 교체한다.
- 수신 때 형식·버전·체크섬·개정 순서를 확인하고, 통과한 데이터만 로컬 트랜잭션으로 적용한다.
- 편집자는 정의 게시 전 기준 개정과 잠금을 확인한다. 다른 개정이 발견되면 자동 병합하지 않고 충돌로 표시한다.
- 공유 엔터티 삭제는 삭제 표시 또는 취소로 전파한다. 이력이 있는 배정을 물리적으로 지우지 않는다.

SQLite 파일은 각 PC에만 둔다. 전체 DB 복사·병합은 하지 않는다. NAS 접근 권한, 원자적 교체와 잠금 동작은 실제 공유 프로토콜에서 검증해야 한다.

## 가져오기와 외부 참조

가져오기는 파일 선택 → 열 매핑 → 형식 검사 → 중복 후보와 변경 미리보기 → 사용자 확인 → Service 일괄 적용 순서다. 첫 템플릿에서 코드 버전은 Scope, 모델·단위·통합은 Category, Codebeamer 대상 함수는 WorkItem의 외부 참조로 매핑한다. 외부 참조는 링크와 ID만 저장하며 첫 버전은 API 호출을 하지 않는다.

## 보안과 복구

실제 업무 내용과 NAS 위치는 공개 저장소·예시·테스트 fixture에 넣지 않는다. 로컬 DB와 NAS 스냅샷의 접근 권한을 OS와 NAS 계정으로 제한한다. 스냅샷 손상이나 schema_version 불일치는 격리하고 기존 로컬 데이터를 유지한다. 백업은 로컬 DB와 공유 스냅샷을 각각 대상으로 하며, 복구 절차는 실제 PC·NAS에서 검증한 뒤 운영 문서에 기록한다.
