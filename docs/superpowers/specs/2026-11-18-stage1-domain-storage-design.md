# 1단계 설계: 도메인, 로컬 SQLite, 완료 근거와 확인, 속도

작성일: 2026-11-18. 상태: 승인 대기.

## 의도

`docs/implementation-plan.md` 1단계를 구현한다. NAS 없이 업무 생성·배정·진행 갱신이 로컬에 저장되고 재시작 후에도 조회된다. 여기에 사용자가 추가한 요구 두 가지를 넣는다.

- 담당자별 속도를 모두가 볼 수 있다.
- 안 끝난 일을 끝났다고 올리는 것을 어렵게 한다. 완료에는 근거가 필요하고, 편집자가 확인해야 믿을 수 있는 완료가 된다.

## 목표

- 프로젝트, 범위, 분류, 업무, 배정, 진행, 이력, 완료 확인, 전송 대기를 로컬 SQLite에 저장한다.
- 권한 위반과 잘못된 입력은 저장되지 않는다.
- 진행 변경은 진행 값, 이력, 전송 대기를 한 트랜잭션에 기록한다.
- 속도와 현황은 저장하지 않고 원본 행에서 계산한다.
- 화면 시안(아래 "화면이 요구하는 것")의 모든 조회와 동작을 Service가 제공한다.

## 하지 않는 것

- 화면(2단계), 엑셀 입출력(3단계), NAS 공유와 SnapshotCursor(4단계).
- 표시 이름을 담는 사용자 테이블. 사용자 ID는 의미를 해석하지 않는 문자열이다.
- 파일 첨부, 업무 크기 가중치, 공수 예측.
- 링크가 실제로 열리는지 검사하는 것.

## 이렇게 되면 실패다

- 담당자가 혼자서 "확인된 완료"를 만들 수 있다.
- 속도 숫자를 누군가 직접 입력하거나 고칠 수 있다.
- 편집자가 담당자의 진행 값을 대신 쓴다.
- Service API로 이력을 고치거나 지울 수 있다.

## 제약

- 의존성 없음. 표준 라이브러리 `sqlite3`, `hashlib`, `unittest`만 쓴다. Python 3.11 이상.
- 화면 → Service → Repository → SQLite. Service 밖에서 SQL을 쓰지 않는다.
- 모든 공유 엔터티 ID는 UUIDv4 문자열, 시각은 UTC ISO-8601, 기한은 `YYYY-MM-DD`.
- 삭제는 삭제 표시(업무)와 취소(배정)로만 한다.
- 0단계 결정표의 가정(한 행 = 한 배정, 진행도 0~100, 사용자 ID는 문자열)을 그대로 쓰고 코드에 가정임을 적는다.

## 접근 방식

| 선택지 | 내용 | 판단 |
| --- | --- | --- |
| A. 근거 필수만 | 완료 때 근거를 입력하고 모두에게 보인다 | 아무도 열어 보지 않으면 형식적 근거로 통과한다 |
| B. 근거 필수 + 편집자 확인 | A에 더해 편집자가 확인 또는 반려를 남긴다 | **사용자가 선택.** 본인 혼자 확인된 완료를 만들 수 없다 |
| 확인을 상태로 둠 | "검토 대기" 상태를 추가한다 | 기각. 편집자가 담당자의 상태를 쓰게 되어 기존 규칙과 충돌하고 담당자가 확인을 기다리게 된다 |
| ORM 사용 | SQLAlchemy 등 | 기각. 테이블 10개에 의존성과 배포 부담만 늘어난다 |

B에서 확인은 편집자가 따로 쓰는 추가 전용 기록이다. 저장 방식은 `sqlite3`와 직접 쓴 SQL이다.

## 사용자가 정한 것

- 완료에는 근거가 필요하다.
- 편집자가 완료를 확인하거나 반려한다(B).
- 담당자별 속도는 모두에게 보인다.
- 화면 구성은 2026-11-18 시안을 따른다.

## 내가 정한 것 (틀리면 고친다)

### 권한

- 프로젝트를 만든 사람이 첫 편집자다. 편집자는 다른 편집자를 추가할 수 있다.
- 정의(범위, 분류, 업무, 배정)는 그 프로젝트의 편집자만 쓴다.
- 진행은 그 배정의 담당자만 쓴다. 편집자여도 남의 진행은 못 쓴다.
- 완료 확인은 그 프로젝트의 편집자만 쓰고, 자기가 담당자인 배정은 확인할 수 없다. 그래서 편집자가 한 명뿐인 프로젝트에서 그 편집자가 맡은 업무는 확인 대기로 남는다. 의도한 동작이다. 풀려면 편집자를 한 명 더 추가한다. 편집자 해제는 이번 범위에 없다.
- 배정의 담당자는 바꿀 수 없다. 담당자를 바꾸려면 기존 배정을 취소하고 새 배정을 만든다. 진행과 이력은 새 배정으로 넘어가지 않는다. 기한은 편집자가 고칠 수 있다.
- 조회는 제한하지 않는다. 속도 포함.

### 상태와 진행 규칙

| 상태 | 진행도 | 추가 조건 |
| --- | --- | --- |
| 미시작 | 0 | 근거·보류 사유 없음 |
| 진행 중 | 0~99 | 없음 |
| 보류 | 0~99 | 보류 사유 필수 |
| 완료 | 100 | 근거 참조 필수. 설명과 결과(통과·실패·해당 없음)는 선택 |

- 필수 문자열은 앞뒤 공백을 지운 뒤 비어 있으면 거부한다.
- 상태 사이의 이동은 모두 허용한다. 완료를 다시 진행 중으로 되돌릴 수 있다.
- 취소된 배정과 삭제 표시된 업무의 배정은 진행을 바꿀 수 없다.

### 이력

- 진행이 바뀔 때마다 새 값 전체를 한 행으로 추가한다. 이전 값은 앞 행이다.
- 시각은 Service에 주입한 시계가 찍는다. 호출자가 넘기지 않는다.
- 진행 값이 하나도 바뀌지 않은 저장은 무시하고 이력을 남기지 않는다. 새 배정은 이력 행 없이 미시작으로 본다.
- 사슬은 (프로젝트, 작성자) 단위다. 전송 대기와 4단계 스냅샷의 단위와 같아야 다른 PC가 스냅샷 하나만으로 검사할 수 있다. 완료 확인 기록에는 사슬을 두지 않는다. 막으려는 것은 담당자의 조작이고 확인 기록은 담당자가 쓰지 않기 때문이다.
- 각 행은 `prev_hash`와 `hash`를 갖고, `hash`는 `prev_hash`와 그 행의 필드를 정해진 순서의 JSON으로 만든 것의 SHA-256이다. 4단계에서 사용자별 스냅샷으로 나갈 때 다른 PC가 과거 변경을 알아챌 수 있게 하기 위해서다.
- 이력과 완료 확인 테이블은 SQLite 트리거로 UPDATE와 DELETE를 거부한다.
- 사슬을 검사하는 Service 조회를 둔다.

### 완료 확인

- 확인 기록은 "완료를 신고한 그 이력 행"에 묶인다. 필드는 결정(확인·반려), 사유, 확인자, 시각이다. 반려는 사유 필수다.
- 확인과 반려는 현재 완료인 배정의 최신 이력 행에만 남길 수 있다.
- 한 이력 행에 확인 기록이 여러 개면 가장 나중 것이 유효하다(실수 정정용).
- 배정의 확인 상태는 계산한다.
  - 현재 상태가 완료가 아니면: 해당 없음.
  - 완료이고 최신 이력 행에 확인 기록이 없으면: 확인 대기.
  - 있으면 그 결정에 따라: 확인됨 또는 반려됨.
- 담당자가 완료 뒤 근거를 고치면 새 이력 행이 생기므로 다시 확인 대기가 된다. 확인된 뒤에 고쳐도 마찬가지다.

### 속도와 현황

- 속도(프로젝트, 기간): 담당자별로 배정 수, 완료 신고 수, 확인된 완료 수, 반려 수, 주당 확인된 완료를 돌려준다.
  - 기간은 Service가 UTC 시각 두 개로 받는다. 시작은 포함하고 끝은 포함하지 않는다. 현지 날짜를 UTC 시각으로 바꾸는 것은 화면의 일이다.
  - 취소된 배정과 삭제된 업무는 모든 숫자에서 뺀다.
  - 배정 수: 기간과 무관하게 지금 유효한 배정 수.
  - 완료 신고 수: 현재 완료이고 최신 이력 행의 시각이 기간 안인 배정 수.
  - 확인된 완료 수: 그중 확인 상태가 확인됨인 것. 시점은 확인한 때가 아니라 신고한 때다. 확인이 늦어져도 담당자의 속도 시점이 밀리지 않게 하기 위해서다.
  - 반려 수: 그 담당자의 이력 행 가운데 유효한(가장 나중) 확인 기록이 반려이고 그 반려 시각이 기간 안인 행의 수. 확인으로 정정된 반려는 세지 않는다. 반려 뒤 다시 올린 경우 이전 행의 반려는 그대로 센다.
  - 주당 확인된 완료: 확인된 완료 수 ÷ (기간 일수 ÷ 7).
- 현황(프로젝트, 오늘 날짜): 전체, 확인된 완료, 확인 대기, 보류, 기한 초과 건수와 분류별 건수. 취소된 배정과 삭제된 업무는 뺀다. 기한 초과는 기한이 오늘보다 앞이고 완료가 아닌 것이다.
- 건수 기준이라 업무 크기 차이는 반영하지 못한다. 알려진 한계다.

### 전송 대기

- 스냅샷 단위의 "게시 필요" 표시다. 키는 (종류, 프로젝트, 작성자)이고 종류는 정의, 진행, 확인이다. 정의의 작성자는 비워 둔다.
- 변경과 같은 트랜잭션에서 표시한다. 이미 표시돼 있으면 그대로 둔다.
- `docs/architecture.md`의 "변경된 엔터티, 재시도 상태"보다 단순하다. 스냅샷이 파일 전체를 다시 쓰므로 충분하다고 본다. 재시도 상태는 4단계에서 필요해지면 넣는다.

### 구조

- `domain`: 상태·결과·결정 열거형, 진행 규칙 검사, 기한 형식 검사, 이력 해시 계산, 오류 종류(입력 오류, 권한 오류, 없음).
- `storage`: 연결 열기와 스키마 맞추기(`PRAGMA user_version`), Repository.
- `services`: 행위자 ID를 받는 Service 하나. 시계는 생성 때 주입한다.
- 스키마 버전은 1 하나로 시작한다. 외래 키 검사를 켠다.

## 화면이 요구하는 것

| 화면 | Service가 제공할 것 |
| --- | --- |
| 프로젝트·범위·분류 선택 | 프로젝트 목록, 프로젝트의 범위·분류 목록 |
| 업무 목록 | 프로젝트의 배정 행 목록(대상, 범위, 분류, 담당자, 기한, 상태, 진행도, 결과, 외부 참조, 확인 상태). 범위·분류·담당자로 거르기. 검색과 정렬은 화면에서 한다 |
| 내 업무 | 행위자에게 배정된 행 목록 |
| 상세 패널 | 배정 하나의 정의, 현재 진행과 근거, 이력, 확인 기록 |
| 근거 입력 | 진행 갱신(상태, 진행도, 결과, 보류 사유, 근거 참조, 근거 설명) |
| 확인 대기 | 프로젝트에서 확인 대기인 행 목록(행위자가 담당한 것 제외), 확인·반려 |
| 현황·속도 | 현황, 속도 |
| 공유 상태 | 전송 대기 건수 |

## 만드는 사람에게 맡기는 것

- 테이블과 열 이름, 인덱스, 함수 이름과 반환 자료형.
- 해시에 넣는 JSON의 정확한 필드 순서와 표기. 한 번 정하면 테스트로 고정한다.
- 테스트 파일 나누기.

## 테스트로 확인할 것

- 임시 DB 파일을 닫았다가 다시 열어도 업무·배정·진행·이력이 남아 있다.
- 편집자가 아닌 사람의 정의 변경, 담당자가 아닌 사람의 진행 변경, 편집자가 아닌 사람의 확인, 자기 업무 확인이 모두 거부되고 아무것도 저장되지 않는다.
- 상태 규칙 표의 위반(근거 없는 완료, 사유 없는 보류, 진행도 범위, 잘못된 기한)이 거부된다.
- 진행 변경 한 번에 진행 값, 이력 한 행, 전송 대기 표시가 함께 생기고, 중간에 실패하면 셋 다 없다.
- 이력과 확인 기록을 SQL로 직접 고치거나 지우려 하면 실패한다. 사슬 검사가 정상 이력은 통과시킨다.
- 확인 상태 계산: 확인 대기 → 확인됨, 반려됨 → 근거 수정 후 다시 확인 대기, 확인됨 → 근거 수정 후 다시 확인 대기.
- 속도와 현황의 숫자가 작은 예시 데이터에서 손으로 센 값과 같다.
